# Автотесты ESPidi

Стенд для автоматического подтверждения (или опровержения) багов из [docs/TEST_PLAN.md](../docs/TEST_PLAN.md).
Устройство подключено к ПК **двумя** кабелями; тесты формулируют *правильное* поведение:

> **FAIL = дефект подтверждён на железе**, PASS = гипотеза не воспроизвелась.

```
 ПК ── USB-MIDI кабель ──►  MIDI IN  ┐
                            ESPidi   ├─ ПК ── USB (тот же, что для прошивки) ── консоль + метрики
 ПК ◄─ USB-MIDI кабель ───  MIDI OUT ┘
```

* **MIDI** — ПК шлёт ноты/CC/Clock в MIDI IN и пишет всё, что ESPidi выдаёт на MIDI OUT (с метками времени).
* **USB Serial** — тестовая прошивка (окружение PlatformIO `test`) принимает команды: «нажать кнопку»,
  «повернуть энкодер», «выставить параметр», «отдать состояние / экран / EEPROM / файл» — и ведёт
  внутренние метрики (опоздание тиков, зазоры цикла, длительность блокирующих участков, число `EEPROM.commit()`).

## Подготовка

1. **Прошивка.** `pio run -e test -t upload` (или `.\run_tests.ps1 --flash`). Обычная сборка `pio run`
   по-прежнему собирает **немодифицированный baseline** (проверено: бинарник идентичен до вставок).
   Тестовое окружение включает `ARDUINO_USB_CDC_ON_BOOT`, поэтому USB-порт становится консолью.
2. **Python.** `.\run_tests.ps1` сам создаст `tools\.venv` (Python 3.12) и поставит зависимости.
3. **Порты.** `python -m esptest ports` — покажет COM- и MIDI-порты. Если автоопределение MIDI не сработало
   (на ПК несколько MIDI-устройств), задайте подстроки имён:
   `--midi-in "USB MIDI"` (куда пишет MIDI OUT ESPidi) и `--midi-out "USB MIDI"`, либо переменные
   `ESPIDI_MIDI_IN`, `ESPIDI_MIDI_OUT`, `ESPIDI_SERIAL`.

## Запуск

```powershell
.\run_tests.ps1 -m unit                    # проверки самой инфраструктуры, без устройства
.\run_tests.ps1 -k smoke                   # дымовые тесты стенда — запускать первыми
.\run_tests.ps1 --midi-in "USB" --midi-out "USB"     # весь набор (≈ 10 мин)
.\run_tests.ps1 -k "b2 or b4" --long       # выбранные тесты, прогоны в 6 раз длиннее
.\run_tests.ps1 --allow-wipe               # + тесты со стиранием flash (factory reset: настройки и ВСЕ паттерны/песни)
```

Итоги: `tools/results/<время>/summary.md` (+ `results.json`), копия в `results/latest/`. В таблице:
`✔ ДЕФЕКТ подтверждён` · `✘ не воспроизведено` · `≈ поведение — уточнить у Евгения` (тесты с маркером `design`) ·
`! ошибка стенда` (исключение, а не провал assert — смотрите кабель/порт) · `— пропущен`. Под таблицей — метрики
(гистограммы опозданий, максимальные блокировки по функциям, расхождения байтов файла и т. п.).

> ⚠ Используйте **отдельное устройство для разработки**: тесты переписывают EEPROM и паттерны LittleFS.

## Как это устроено

| Уровень | Файл | Что делает |
|---|---|---|
| Прошивка | `Firmware/ESPidi/test_hooks.{h,cpp}` | Консоль и метрики. Компилируется **только** при `-DESPIDI_TEST` (окружение `test`). |
| Вставки в код Евгения | 7 файлов, 40 строк | Только внутри `#ifdef ESPIDI_TEST`: замеры (`TH_SCOPE`), вызовы консоли в `loop()` и `clock_update()`. |
| Виртуальные кнопки | `digitalRead()` → `th_digitalRead()` | Подмена только для проектных исходников (`build_src_flags`): настоящие `inputs_pollButtons()` и `ui_handleButton()` отрабатывают с debounce 30 мс и порогом долгого нажатия 600 мс. Энкодер в прерывании не подменяется — `enc N` добавляет щелчки в `encDelta`. |
| Консоль (ПК) | `esptest/console.py` | Протокол `<id> <команда>` → `@<id> {json}`; обёртки `click`, `combo`, `param`, `state`, `stats`, `screen`, `fs_*`, `reboot`. |
| MIDI (ПК) | `esptest/midi.py` | Захват с метками `perf_counter`, `wait_quiet`, отправка любых сообщений. |
| Часы (ПК) | `esptest/clock.py` | `RealtimeClock` — по расписанию; `SteppedClock` — **один Clock → ждём тишины → следующий**: результат не зависит от джиттера ПК, события привязаны к номеру тика. |
| Анализ | `esptest/analysis.py` | Интервалы Clock, выбросы, зависшие ноты, время на проводе. |
| Допуски | `esptest/thresholds.py` | Пороги «исправной прошивки» в одном месте. |
| Файлы паттернов | `esptest/patterns.py` | Построители `MSEQ` v2 / `SONG` v1 для детерминированных сценариев и побайтового round-trip. |

### Два независимых измерителя тайминга

* **ПК:** интервалы 0xF8. Точность ≈ 1–2 мс (драйвер Windows), шумовой пол измеряется перед тестами (`noise_floor`)
  и вычитается из допуска. Этого достаточно для событий ≥ 5 мс (перерисовка OLED ≈ 12 мс, CC123 ×16 ≈ 15 мс,
  128×NoteOff ≈ 123 мс).
* **ESP32:** `stats` — гистограммы опоздания внутренних тиков, зазоров между точками обслуживания (оценка задержки
  внешнего Clock), итераций `loop()`, и таблица `scopes` с максимальной длительностью блокирующих участков:
  `ui.draw`, `arp.stopSounding`, `mel.stopAll`, `mel.load`, `song.stopAll`, `song.loadBuf`, `save.eeprom`,
  `dispatch_tick`. Не зависит от кабеля и ПК.

### Команды консоли

`ping`, `state`, `stats [reset]`, `events`, `reset`, `virt 0|1`, `press|release enc|lr|tap|play`, `enc N`, `app N`,
`param <метка> [значение]` (обычный путь UI, с побочными эффектами), `screen` (кадр OLED), `eeprom [от длина]`,
`flushsave`, `fs ls|get|put|rm|format`, `load mel|song <слот0>`, `seqdump`, `songdump`, `factory`, `reboot`.

## Покрытие плана тестов

Автоматизировано: **A3, B1–B8, B11–B14, C1–C7, C9, C10, D1, D3–D8, D10–D12, D15, E1, E3–E5, F2, G1–G4, H1, H4**
(+ дымовые S).

Не автоматизировано — нужен человек или иная оснастка:

| ID | Почему |
|---|---|
| A1, A2, F4–F7 | Визуальная оценка экрана и ощущение кнопок (кадр доступен через `screen`, но «красиво ли» решает человек) |
| F1 | Физический энкодер: ISR и дребезг контактов не имитируются |
| B9, B10 | Субмиллисекундный джиттер внешнего Clock — логический анализатор на GPIO10; косвенно: `gap`/`late` в `stats` при H1 |
| H2 | Многочасовой soak — запускается вручную с `--long` (сценарий-заготовка: B4 + B5 в цикле) |
| H3 | Потеря питания во время записи файла |
| C8, D2, D9, D13, D14, E2, E6, E7, H5 | Добавляются по мере необходимости — каркас (`Pattern`, `Song`, `SteppedClock`) готов |

## Ограничения и честные оговорки

* Стенд проверен **без устройства**: тестовая прошивка собирается, Python-часть покрыта unit-тестами
  (`-m unit`, 10 проверок: протокол консоли на фиктивном порту, анализ, форматы файлов, декодер экрана).
  Сценарии на железе ещё не прогонялись — первый запуск начинайте с `-k smoke`.
* Тесты с пометкой `design` показывают расхождение с *ожидаемым*, но возможно задуманным поведением — решает автор.
* На время тестов физические кнопки отключены (`virt 1`); `virt 0` возвращает их.
